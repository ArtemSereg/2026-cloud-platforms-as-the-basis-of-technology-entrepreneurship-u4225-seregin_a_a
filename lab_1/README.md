### Шаг 3. Проверка безопасности (изменение прав)
* Вернулся в панель Google Cloud и отобрал у аккаунта права `Storage Admin`, заменив их на скромную роль `Compute Viewer`.
* Попробовал снова выполнить команды в терминале ВМ. Система позволила скопировать еще раз файлы.

В ходе выполнения лабораторной работы был проведен эксперимент по отзыву прав `Storage Admin` у сервисного аккаунта с целью заблокировать копирование файлов. Однако возникла аномалия: даже после смены роли на `Compute Viewer` файлы из бакета `gs://lab1-bucket-itmo/` продолжали успешно скачиваться на виртуальную машину.

Для поиска причины и устранения проблемы были предприняты следующие шаги:
1. **Ожидание обновления кэша IAM:** Повторные попытки выполнялись через промежутки времени (более 5 минут), так как изменения политик доступа в Google Cloud могут применяться не мгновенно. Результат не изменился — копирование оставалось доступным.
2. **Принудительный сброс авторизации:** Была предпринята попытка очистить кэш токенов внутри ОС с помощью команд утилиты `gcloud`. Данное действие привело к ошибке авторизации (`ACCESS_TOKEN_SCOPE_INSUFFICIENT`), но принципиально проблему с доступом к файлам не решило.

### Техническое обоснование причин аномалии:

На основе проведенных тестов можно сделать вывод о причине такого поведения системы:

**Публичный доступ к исходному бакету (наиболее вероятно):** 
   Бакет `gs://lab1-bucket-itmo/`, созданный для лабораторной работы, имеет статус **Public to internet** (разрешен доступ `allUsers` или `allAuthenticatedUsers`). В этом случае для чтения и скачивания файлов облаку в принципе не нужны права конкретного сервисного аккаунта — файлы открыты для любого пользователя, и отзыв роли `Storage Admin` никак не влияет на команду скачивания.
